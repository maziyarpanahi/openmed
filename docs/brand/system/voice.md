# OpenMed voice

## Core voice

Write with clinical restraint and developer precision. Prefer short,
testable statements over superlatives. Lead with what a person can do, then
state the boundary that keeps the claim true.

Use **OpenMed** in prose and `openmed` for the visual wordmark, Python package,
CLI, and code identifiers. Use **OpenMedKit** for the Swift/Apple surface.
Name other products explicitly; never let a library claim silently extend to
OpenMed Agent, Welna, or a third-party model.

## Claims

- Pull numbers and dated facts from `claims.yml`; do not type them into art.
- State whether a language is supported, model-backed, placeholder-routed,
  validator-only, or user-configured.
- Say **Apache-2.0 SDK** for the OpenMed software license. Model and dataset
  licenses vary and must be checked at their source repositories.
- Say **open models** only for a named population with verified availability.
  Do not call a population open-source without verifying every license.
- Qualify local/offline behavior by runtime and configuration. Do not promise
  compliance, medical-device status, or that an integration makes a deployment
  compliant.
- Avoid `#1`, `best`, `SOTA`, `fully compliant`, `zero risk`, and live-looking
  counters unless the registry has current, scoped evidence.

## Social and profile copy

Preferred stable tagline:

> Local-first clinical AI. Apache-2.0 SDK.

Preferred short description:

> Build clinical extraction and de-identification workflows on hardware you
> control. Model and dataset terms vary by source.

Social art should use stable capability language, not download, install,
repository, model, language, or release-cadence totals.

## Alt text

Describe the useful identity and message, not decorative geometry. Keep it
concise and localized. Example:

> OpenMed — local-first clinical AI with an Apache-2.0 SDK

For the cat, say “OpenMed cat crest” when its presence is relevant. Do not
repeat metric text already adjacent to the image.
