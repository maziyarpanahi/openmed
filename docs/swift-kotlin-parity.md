# Swift-Kotlin OpenMedKit Parity

OpenMedKit keeps one public mobile contract across Swift and Kotlin. This
checklist pins the required Android symbols against the Swift package symbols
so API drift is caught in tests instead of downstream apps.

## Public API Baselines

Both kits commit a baseline of their full public API, and CI compares the
code with it on every pull request that touches the kit.

| Kit | Baseline | Generated by | CI check |
| --- | --- | --- | --- |
| Swift, macOS | `swift/OpenMedKit/api/macos/<Module>.json` | `swift-api-digester -dump-sdk` on a `swift build` | `Swift Package (OpenMedKit)` / Build & Test OpenMedKit |
| Swift, iOS Simulator | `swift/OpenMedKit/api/ios/<Module>.json` | `swift-api-digester -dump-sdk` on an `xcodebuild` iOS Simulator build | `Swift Package (OpenMedKit)` / Check iOS Swift API baseline |
| Kotlin | `android/openmedkit/api/openmedkit.api` | Kotlin binary-compatibility validator (`apiDump`) | `Android CI (OpenMedKit)` / `apiCheck` |

The Swift baselines cover the five library products of the root
`Package.swift`: `OpenMedKit`, `OpenMedSpeech`, `OpenMedExtensionSupport`,
`OpenMedShareExtension` and `OpenMedActionExtension`. The iOS baseline is the
one that records the UIKit-only Share and Action extension classes.
`scripts/release/swift_api_baseline.py` turns each digester dump into a
toolchain-neutral list of declarations keyed by module-qualified symbol, such
as `OpenMedKit.OpenMed.analyzeText`. It records argument labels, parameter and
result types, which parameters have defaults, `async` and `throws`, accessors,
conformances and generic signatures. Raw digester JSON is not committed
because it contains local paths and Xcode-specific fields.

What fails CI:

- **A removed or changed declaration** fails the platform check, and the log
  names each symbol. The Swift check prints the old and new declaration. The
  Kotlin `apiCheck` prints a diff of the `.api` file.
- **A refreshed baseline that removes or changes a declaration** also needs a
  `docs/migration/*.md` file that is added or modified in the same pull request
  and names every affected symbol. The `api-migration-policy` jobs run
  `scripts/release/check_native_api_migration.py` to enforce this, in the same
  way the Python `api_surface_diff.py --check` gate does for Python. Write the
  symbol exactly as the gate prints it: `OpenMedKit.OpenMed.analyzeText` for
  Swift (a trailing label list such as `(_:confidenceThreshold:)` is allowed)
  and `com.openmed.openmedkit.OpenMedModelStore.isMLXModelCached` for Kotlin.
- **Additions** never need a migration entry. The Swift check lists symbols
  missing from the baseline without failing. Kotlin `apiCheck` requires an
  exact match, so run `apiDump` when you add public Kotlin API.

Regenerate the baselines after an intended API change and commit the result
with the source change:

```bash
# Swift, macOS (from the repository root)
swift build
python3 scripts/release/swift_api_baseline.py --platform macos --update

# Swift, iOS Simulator
xcodebuild build -scheme OpenMedKit-Package \
  -destination 'generic/platform=iOS Simulator' \
  -derivedDataPath .build/xcode-ios -skipPackagePluginValidation
python3 scripts/release/swift_api_baseline.py --platform ios --update

# Kotlin (JDK 17)
cd android && ./gradlew :openmedkit:apiDump
```

Run the checks locally with `--check` in place of `--update`,
`./gradlew :openmedkit:apiCheck`, and the migration gate against your target
branch:

```bash
python3 scripts/release/check_native_api_migration.py --base origin/master
```

Pass `--head WORKTREE` to include uncommitted files.

A new Xcode release can change how the digester prints a type or which
conformances an SDK class reports. If the Swift check fails on a pull request
that did not touch the API, the toolchain changed: refresh the baselines in a
separate pull request. New SDK conformances only add lines and need no
migration entry; a refresh that rewrites existing lines still goes through the
migration gate. On failure, CI uploads the regenerated baselines as the
`swift-api-baseline-macos` or `swift-api-baseline-ios` artifact.

## Shared Span Fixture

Both mobile kits use the same synthetic fixture files:

- `fixtures/parity/synthetic_clinical_note.txt`
- `fixtures/parity/expected_spans.json`

The fixture is synthetic and contains invented names, dates, contact details,
and record identifiers. `expected_spans.json` stores only `label`, `start`, and
`end` so platform tests compare offsets without depending on confidence scores
or model-specific metadata.

The Kotlin tests register `fixtures/parity` as a JVM test resource directory in
`android/openmedkit/build.gradle.kts`. `SpanEquivalenceTest` reads the note and
expected spans from the test classpath, runs `OpenMed.extractPII(...)`, and
asserts exact span equivalence.

Swift tests should consume the same files from the repository root instead of
copying fixture data into the Swift package. A Swift test can resolve the repo
fixture directory relative to the package checkout and decode the expected
spans with `JSONDecoder`, then compare `EntityPrediction.label`,
`EntityPrediction.start`, and `EntityPrediction.end` against the shared JSON.
Keeping both tests on these root-level files makes fixture changes explicit in
one diff.
