# Migrating from OpenMed 3.3 to 4.0

OpenMed `4.0.0` is the next breaking release and is not published yet. This
guide collects each breaking change as it lands, with the migration it needs.
The [fixed-option decision API](../api/fixed-option-decisions.md) and
[local decision models](../decision-models.md) pages describe the current
contracts in full.

## Decision schema 1.2.0

The decision request and result schemas are now version `1.2.0`. Two changes
landed after `1.1.0` was published without a version bump, so the `1.1.0`
`$id` named two different documents. They now belong to `1.2.0`:

- requests may carry verified local `media`;
- backend license provenance is a bounded license expression with an optional
  `license_sha256`, and may appear in results of every `1.x` version.

Migrate as follows:

- A request that omits `schema_version` resolves to the lowest version carrying
  every field it uses: `1.0.0`, `1.1.0`, or `1.2.0` when it carries `media`.
  Existing `1.0.0` and `1.1.0` requests decide exactly as before and keep their
  result version.
- A request that declares `schema_version: "1.1.0"` and carries `media` is now
  refused with `input_error`. Declare `"1.2.0"` or omit the version. Code that
  adds media to an existing request with `dataclasses.replace` must also set
  `schema_version="1.2.0"` or `None`.
- Validators pinned to `https://openmed.dev/schemas/decision-request/1.1.0` or
  `.../decision-result/1.1.0` should load the `1.2.0` documents, which accept
  every `1.0.0`, `1.1.0` and `1.2.0` payload.
- `DECISION_SCHEMA_VERSION` is now `"1.2.0"`, and
  `migrate_decision_result()` migrates to `1.2.0` by default. Pass
  `target_version="1.1.0"` to keep the previous label; results have the same
  fields at `1.1.0` and `1.2.0`.
- The TypeScript client's `schema_version` fields use the new
  `DecisionSchemaVersion` union, which includes `"1.2.0"`.

Every published version of each decision document is now pinned by
fingerprint, so a future schema change fails CI until the version is bumped.

## One `/v1/decisions` route for both request shapes

OpenMed's own `DecisionServerBackend` posted the OpenAI-compatible Decisions
body (`model`, `input`, `questions`) to `/v1/decisions`, where the OpenMed
route required `mode` and `input_text`. An OpenAI-compatible client, or one
OpenMed service bridging to another, received a `422`.

The route now negotiates the body. It recognises an OpenMed request by `mode`
or `input_text` and an OpenAI-compatible body by `model` or `input`, and
answers in the same shape. `questions` exists in both shapes and decides
nothing. The path stays shared rather than split. Moving the OpenMed route
would break every existing OpenMed client, and giving the OpenAI-compatible
body its own path would leave those clients unable to call `/v1/decisions`
unchanged. The required keys of the two shapes never overlap, so one path
serves both.

What changes:

| Before | After | Migration |
| --- | --- | --- |
| An OpenAI-compatible body failed with `validation_error` | It is decided and answered with `model`, `answers` and an `openmed` review object | Name the served backend's `model_id` in `model`; send text only |
| A body with keys of both shapes failed with `validation_error` | `422 decision_request_ambiguous`, `details.reason: both_shapes` | Send one shape |
| A body with keys of neither shape failed with `validation_error` | `422 decision_request_ambiguous`, `details.reason: no_shape` | Send `mode` and `input_text` |
| Validation errors named fields as `body.input_text` | They name the shape first, for example `body.openmed.input_text` | Match on the last path segment or on `error.code` |
| — | An OpenAI-compatible body with `media` is refused with `422 decision_media_unsupported` | Send media in an OpenMed `1.2.0` request |
| — | An OpenAI-compatible `model` that is not the served model is refused with `422 model_not_served` | Name the served model |

Valid OpenMed requests keep their results. Both shapes use the same
`decisions:write` scope, request-body limit, access policy, backend and
calibration profiles. The OpenAI-compatible body carries no OpenMed policy
fields, so it is decided under the defaults (namespace `default`, purpose
`care_review`, the default calibration, 5,000 ms and 8,192 characters); send an
OpenMed request when you need other policy fields.

To bridge one OpenMed service to another, set the backend's `model_id` (or
`served_model`) to the remote service's backend `model_id`:

```python
# Fragment: needs a second OpenMed service listening on loopback.
from openmed.structured import decide
from openmed.structured.decision_server import DecisionServerBackend

backend = DecisionServerBackend(
    endpoint="http://127.0.0.1:8081",
    protocol="openai_decisions",
    model_id="openmed/deterministic-fixed-option",
    revision="1.0.0",
    license_id="Apache-2.0",
)
result = decide(request, backend=backend)  # route the result for human review
```

The typed clients add one method for the new shape: Python
`OpenMedClient.openai_decisions()`, TypeScript `openaiDecisions()` and Go
`OpenAIDecisions()`. `decision()` and `Decision()` are unchanged.
